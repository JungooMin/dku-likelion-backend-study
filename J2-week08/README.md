# J2-week08

## Spring Boot REST API와 요청별 인증 처리

이번 주차에서는 기존 URL 단축 서비스(SURL)의 기능을 REST API 방식으로 구현하고, 데이터 전달과 데이터베이스 접근을 효율적으로 관리하는 방법을 학습했다.

또한 HTTP 요청마다 사용자를 확인하는 인증 방식과, 반복적인 데이터 조회를 줄이기 위한 메모리 캐싱의 개념을 이해했다.

---

## 1. REST API와 CRUD

REST API는 HTTP 메서드를 활용하여 서버의 자원을 조회하거나 변경할 수 있도록 설계한 API이다.

이번 실습에서는 URL 단축 서비스의 등록, 단건 조회, 목록 조회, 수정, 삭제 기능을 REST API 형태로 구성했다.

| HTTP 메서드 | API 경로 | 기능 |
|---|---|---|
| POST | `/api/v1/surls` | URL 등록 |
| GET | `/api/v1/surls/{id}` | URL 단건 조회 |
| GET | `/api/v1/surls` | URL 목록 조회 |
| PUT | `/api/v1/surls/{id}` | URL 수정 |
| DELETE | `/api/v1/surls/{id}` | URL 삭제 |

REST API에서는 URL로 자원을 표현하고 HTTP 메서드로 수행할 작업을 구분한다.

예를 들어 `/{id}`는 경로 변수로, `@PathVariable`을 사용하면 해당 위치의 값을 메서드 매개변수로 전달받을 수 있다.

이러한 구조는 API의 일관성을 높이고, 프론트엔드와 백엔드 사이의 통신을 명확하게 만든다.

---

## 2. DTO(Data Transfer Object)

DTO는 계층 간 또는 서버와 클라이언트 사이에서 데이터를 전달하기 위한 객체이다.

### DTO가 필요한 이유

JPA의 Entity는 데이터베이스와 연결된 객체이므로, API 응답으로 직접 반환하면 내부 데이터 구조가 외부에 노출될 수 있다.

또한 Entity의 필드가 변경되면 클라이언트가 사용하는 응답 형식까지 변경될 위험이 있다.

따라서 Entity와 DTO를 분리하여 외부에 필요한 데이터만 전달하도록 설계하는 것이 좋다.

```text
Database
    ↓
Entity (데이터베이스 모델)
    ↓
DTO (전달할 데이터 구성)
    ↓
JSON 응답
    ↓
Client
```

이번 실습에서는 `SurlDto`, `MemberDto`, `ArticleDto`를 활용하여 Entity를 DTO로 변환하는 방법을 학습했다.

특히 작성자 객체 전체를 전달하는 대신 작성자 ID와 이름처럼 필요한 정보만 선택적으로 포함할 수 있다.

이를 통해 내부 데이터 구조와 API 응답 구조 사이의 의존성을 줄일 수 있다.

---

## 3. OSIV와 트랜잭션

### OSIV(Open Session In View)

OSIV는 HTTP 요청을 처리하는 동안 JPA의 영속성 컨텍스트를 응답 생성 단계까지 유지하는 기능이다.

OSIV가 활성화되어 있으면 트랜잭션이 끝난 후에도 지연 로딩이 가능해 개발이 편리하다.

하지만 데이터베이스 접근이 웹 계층까지 확장되고, 상황에 따라 DB 커넥션의 점유 시간이 길어질 수 있다는 단점이 있다.

이번 실습에서는 다음 설정으로 OSIV를 비활성화했다.

```yaml
spring:
  jpa:
    open-in-view: false
```

OSIV를 끄면 데이터베이스 접근이 필요한 범위를 트랜잭션 안에서 명확하게 관리해야 한다.

- `@Transactional(readOnly = true)`: 데이터 조회 중심의 작업에 사용
- `@Transactional`: 데이터 저장, 수정, 삭제 등 변경 작업에 사용

일반적으로 비즈니스 로직이 수행되는 Service 계층에서 트랜잭션을 관리하는 것이 권장된다.

### Dirty Checking(변경 감지)

JPA는 영속성 컨텍스트가 관리하는 Entity의 변경 사항을 감지하여 데이터베이스에 반영할 수 있다.

이를 Dirty Checking이라고 한다.

트랜잭션 안에서 Entity의 값을 변경하면 별도의 UPDATE 메서드를 직접 호출하지 않아도 변경된 내용을 DB에 반영할 수 있다.

변경된 값이 없다면 불필요한 UPDATE SQL 실행을 줄일 수 있다는 장점이 있다.

## 4. 인증과 권한 검사

HTTP는 기본적으로 무상태(Stateless) 프로토콜이다.

즉, HTTP 요청 자체가 이전 요청의 사용자 정보를 자동으로 기억하거나 전달하지는 않는다.

따라서 사용자를 구분해야 하는 API에서는 요청과 연결된 인증 정보를 확인하는 과정이 필요하다.

- **인증(Authentication):** 요청한 사용자가 누구인지 확인하는 과정
- **인가(Authorization):** 확인된 사용자가 해당 자원에 접근하거나 작업할 권한이 있는지 판단하는 과정

이번 실습에서는 URL 단축 서비스에서 다른 사용자의 데이터를 임의로 수정하거나 삭제하지 못하도록 작성자와 요청 사용자를 비교하는 기능을 구현했다.

권한 확인 로직은 `AuthService`로 분리하여 여러 API에서 공통으로 사용할 수 있도록 구성했다.

### 요청별 인증 방식

이번 강의에서는 매 요청에 아이디와 비밀번호를 포함시키고, 서버에서 해당 정보를 확인하여 사용자를 식별하는 방식을 학습했다.

```text
클라이언트 요청
      ↓
아이디와 비밀번호 확인
      ↓
회원 정보 조회
      ↓
사용자 인증
      ↓
접근 권한 확인
      ↓
API 기능 수행
```

이 방식은 인증 원리를 이해하기 위한 기초적인 실습 방법이다.

실제 서비스에서는 비밀번호를 요청 파라미터로 반복 전달하는 방식을 피하고, HTTPS와 안전한 비밀번호 저장 방식, 세션 또는 토큰 기반 인증 등을 활용해야 한다.

## 5. Request Scope와 메모리 캐싱

### Request Scope

Spring의 `@RequestScope`는 HTTP 요청마다 별도의 Bean 인스턴스를 생성하도록 하는 기능이다.

이번 실습에서 사용한 `Rq` 클래스는 현재 요청과 관련된 정보를 관리하는 Request Scope Bean이다.

`Rq`를 활용하면 여러 Controller에서 인증 처리 코드를 반복적으로 작성하지 않고 `rq.getMember()`를 통해 현재 요청의 사용자 정보를 가져올 수 있다.

### 메모리 캐싱

캐싱은 이전에 계산하거나 조회한 결과를 저장해 두었다가 다시 사용하는 방식이다.

이번 실습에서는 하나의 요청에서 `rq.getMember()`가 여러 번 호출되는 상황을 고려하여 회원 정보를 메모리에 저장하도록 구성했다.

```text
첫 번째 getMember() 호출
        ↓
회원 정보 조회 및 인증
        ↓
Member 객체 저장
        ↓
두 번째 getMember() 호출
        ↓
저장된 Member 객체 재사용
```

- **첫 번째 호출:** 인증 정보를 확인하고 회원 데이터를 조회
- **이후 호출:** 이미 조회한 회원 객체를 반환

이를 통해 하나의 HTTP 요청에서 불필요하게 반복되는 데이터베이스 조회를 줄일 수 있다.

`Rq`는 Request Scope이므로 저장된 정보는 해당 요청 내에서만 재사용되며, 서로 다른 요청 간에 공유되지 않는다.

## 6. 전체 요청 처리 구조

이번 주차에서 구현한 REST API의 주요 처리 흐름은 다음과 같다.

```text
Client
   ↓ HTTP 요청
ApiV1SurlController
   ↓
Rq (현재 사용자 확인)
   ↓
AuthService (권한 검사)
   ↓
SurlService (비즈니스 로직)
   ↓
Repository → Database
   ↓
Entity → DTO 변환
   ↓
RsData (응답 데이터 구성)
   ↓
Client
```

실제 요청에서는 자원을 조회한 뒤 권한을 확인하는 등 API 기능에 따라 처리 순서가 달라질 수 있다.

이처럼 요청 처리, 인증, 권한 검사, 데이터 접근, 응답 변환의 역할을 분리하면 코드의 재사용성과 유지보수성을 높일 수 있다.

---

## 핵심 정리

이번 주차에서는 REST API의 CRUD 구현을 시작으로, 데이터를 안전하고 효율적으로 처리하기 위한 여러 개념을 학습했다.

- **REST API:** HTTP 메서드와 자원 중심 URL을 활용한 데이터 처리
- **DTO:** Entity와 API 응답 객체를 분리하여 데이터 노출 범위 관리
- **OSIV:** 영속성 컨텍스트의 유지 범위를 조절하고 DB 접근 구조 개선
- **Dirty Checking:** Entity의 변경 사항을 감지하여 데이터베이스에 반영
- **인증 및 권한 검사:** 요청 사용자를 확인하고 자원에 대한 접근을 제어
- **Request Scope:** HTTP 요청마다 독립적인 객체를 생성하고 관리
- **메모리 캐싱:** 반복적인 데이터 조회를 줄여 처리 효율 개선

특히 이번 학습을 통해 **Entity와 DTO의 역할을 분리하는 이유, OSIV와 트랜잭션의 관계, HTTP 요청마다 사용자 정보를 확인하고 재사용하는 과정**을 이해할 수 있었다.
